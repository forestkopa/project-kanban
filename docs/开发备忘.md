### 3.1 看板列宽
- 列宽 = 6 列正好占满看板：`.col { flex: 0 0 calc((100% - 80px) / 6) }`（80 = 5×16 gap）。
- **少于 6 个阶段：不铺满，按 6 列尺寸排列、右侧留白**；恰好 6 个阶段一屏放满；超过 6 个阶段横向滚动（列宽保持）。
- 历史教训：固定 264px 在常见视口 6 列会溢出滚动（被否）；均分铺满 flex:1（被否，因为 <6 阶段也铺满了）。**当前 calc 方案是用户认可的**。

## 4. 甘特公式级联引擎（关键机制）

- 导入解析只认「甘特方言」：有 `内容` 列、无 `阶段` 列、日期在 **D/E 列**、`天数`在 **F 列**、单元格带 `WORKDAY.INTL(...)` 公式 → 捕获 `startRule/dueRule` → 甘特级联。
- 参考模版列布局：`任务|内容|负责人|开始|截止|天数|状态|备注`；首任务开始 `=WORKDAY.INTL($B$1,0)`（B1=项目开始日期），后续 `=WORKDAY.INTL(E上一行,1)`，截止 `=WORKDAY.INTL(D本行,F本行-1)`。
- `evalRule` 的 `off` 类型：base 是数字（F 列天数）时做数值偏移，不是日期（曾因把 F4-1 当日期导致级联 NaN，已修）。
- 状态列默认留空（写"未完成"会被 `/完成/` 误判已完成）。

### 8.1 每次 push 同步 release（约定）
- 用户要求：每次 push 到 GitHub 必须同步更新 Release；且**版本号最大的即 latest，随版本滚动**（2026-08-25 明确：不要单独的「rolling」release，latest 即最大版本号）。已落地为**脚本方案**：用 `tools/sync-release.ps1` 代替裸 `git push`。
  - 用法（powershell）：
    - 普通 push：`$env:GH_PAT="ghp_xxx"; .\tools\sync-release.ps1` → 仅 `git push origin main`（不改版本号 / latest）。
    - 发版：`$env:GH_PAT="ghp_xxx"; .\tools\sync-release.ps1 -Version v1.2` → 推送 main + 在最新提交打**不可变**标签 `v1.2` + 创建/更新 `v1.2` Release（变更说明）+ 把 `latest` 标签**滚动**到该提交。版本号由人指定，脚本不自增。
  - **版本号约定（用户 2026-08-25 确定）**：
    - `latest` 标签 = **移动指针**，始终指向「当前最大版本号」对应的提交（当前 = `v1.1`）。发布更高版本（如 `v1.2`）后，`latest` 标签移动到新提交，旧版本（`v1.1`）即不再带 `latest`。
    - `vX.Y` 标签 = **不可变里程碑**（一次创建、永久保留），对应同名 GitHub Release（含本版本变更说明）。
    - GitHub 的 "Latest" 徽标：被 GitHub 自动赋予**最新发布的 release**（即当前最大版本号，v1.1 → 发布 v1.2 后自动切换），无需手动管理。
    - 当前版本 = `v1.1`；下次更新递增为 `v1.2`（功能迭代 v1.x / 重大重构 v2.0）。
  - **关于 `latest` 标签名**：曾一度误以为 `latest` 是 GitHub 保留词（会删自定义 release），改用 `rolling` 标签 + `Rolling (main)` Release；后经验证 `latest` 作为 git 标签完全可用（所谓"消失"实为删除操作所致），且更符合用户「latest = 最大版本号」的心智模型，故回退为 `latest` 标签（不建单独 latest release，徽标由 GitHub 自动管理）。`Rolling (main)` Release 已删除。
- **为什么不用 GitHub Actions 工作流**：曾写 `.github/workflows/release.yml`（push main 自动更新 latest release），但推送被拒——当前 PAT 仅有 `contents` 权限、**缺 `workflow` 作用域**，无法推送 workflow 文件。若日后给 PAT 加 `workflow` 作用域，可改回 CI 自动同步（工作流内容已设计好，逻辑同脚本）。
- **脚本运行注意（本机验证要点）**：脚本内 git 走显式路径解析（先 `Get-Command git`，失败回退常见安装路径），push 走带 PAT 的远端 URL；若 PowerShell 执行策略禁止直接运行 `.ps1`，用 `powershell -ExecutionPolicy Bypass -File .\tools\sync-release.ps1` 运行。本沙箱 PowerShell 因执行策略/路径问题无法直接跑通脚本，但脚本内的 push / 打标签 / GitHub API 三步已用等价直接命令逐一验证可用，故 release 同步机制成立。

### 8.2 Release body 模板踩坑（v1.1 已修）
- **症状**：早期手动跑 Python 创建 `v1.1` Release 时，body 字符串没用 f-string，结果 `{SHA}` `{MSG}` `{REPO}` 当成了字面字符显示在页面上；且 v1.1 Release 标题是简单 "v1.1"，没有描述性。
- **修复**：用 `f"…{var}…"` 或 f-string 三引号字符串，拼接真实数据后再调 API。v1.1 Release 现标题为 `v1.1`、body 为「v1.0→v1.1 变更说明」（多用户 / SQLite / NSSM 自启 / 固定公网域名 / 版本号方案），由 `tools/sync-release.ps1` 在 `-Version v1.1` 时写入。
- **GitHub API 注意**：`PATCH /releases/tags/{tag}` 会返回 404——修改 Release 必须先 `GET /releases/tags/{tag}` 拿 `id`，再 `PATCH /releases/{id}`。GET 路径用 tag，PATCH 路径用 id。
- **预防**：`tools/sync-release.ps1` 里 v1.x body 走 PowerShell here-string + 变量插值（`$sha` / `$msg` / `$repo`），无 `{PLACEHOLDER}` 字面量风险；但若用 Python/JS 临时脚本调 API，**务必**用 f-string / 模板字符串先插值再发请求。

## 9. 安全加固（2026-08-25，基于代码评估报告落地）

- **安全响应头**：`server.js` 统一加 `SEC_HEADERS`（CSP / X-Frame-Options: DENY / X-Content-Type-Options: nosniff / Referrer-Policy / HSTS），API JSON 响应加 `Cache-Control: no-store`，静态文件同样附带。
- **AI Key 不入盘**：支持环境变量 `KB_AI_API_KEY` 优先；设置了环境变量时 `data/ai.json` 不再写入真实密钥（写盘时置空，读取时从环境变量注入）。
- **密码日志移除 + 首登强制改密**：启动日志不再打印 `admin / 000000`；用默认密码登录时 `/api/login` 返回 `mustChange:true`，前端自动弹改密框；`db.js` 不再导出 `DEFAULT_PASSWORD`。
- **记住密码不存明文**：前端「记住我」只保存用户名（`kb-remember` 只存 `{name}`），密码不再写入 localStorage。
- **Token 过期**：`tokens` 表新增 `expires_at`（默认 30 天，可用 `KB_TOKEN_TTL_DAYS` 覆盖）；校验时过期即删；启动时清理过期 token；旧 token（无 expires_at）兼容不过期。
- **登录/AI 限流**：内存限流器——登录每 IP 10 次/15 分钟（429）；AI 接口（chat/generate-tasks/summarize）每用户 30 次/分钟；过期桶每小时清理。
- **config.yml 不再入库**：已加入 `.gitignore` 并从 git 索引移除（`git rm --cached config.yml`，本地文件保留）；仓库提供 `config.example.yml` 占位模板。
- **同步 I/O 异步化**：`loadJSON`/`saveJSON` 改 `fs.promises`（原子写保持：临时文件→rename）；`isRO()` 1s 缓存异步读；`gitAutoCommit` 改为 2s 防抖 + 单进程串行（`git add … && git commit …`），避免高频写入产生并发 git 进程。启动期/低频路径（`/api/readonly` 切换、logo 上传、初始建库）仍保留同步 I/O，可接受。
- **xlsx 依赖完整性**：`package-lock.json` 中 `xlsx` 条目已含 `integrity`（sha512），npm install/ci 时会强制校验；`package.json` 的 CDN URL 不变（沙箱无外网未能独立验算哈希，机制已由 npm 兜底）。
- **验证**：`node --check` 三文件通过；临时实例（PORT=5199）实测——首页/API 安全头齐全、`/api/templates` 200（异步加载）、登录返回 `mustChange:true`、错密码 401、AI 限流 30×400+5×429、带 token 写操作 200。生产服务（5180）仍运行旧代码，需重启 `kanban-watchdog` 服务后生效。

### 9.1 第二批加固（2026-08-25，两轮独立评审合并版）
- **scrypt 参数提升**：`hashPassword` 改用 `N=2^17, r=8, p=1, keylen=64`，哈希串格式升级为 `N:r:p:salt:hash`；`verifyPassword` 对旧格式 `salt:hash` 按默认参数（N=16384, keylen=32）兼容校验——存量用户密码无需重置。
- **GET 接口统一鉴权**：除 `/api/readonly`、`/api/ai/ollama-models`（公开状态探测）与登录外，所有 GET `/api/*` 均需登录（此前 `/api/templates`、`/api/options`、`/api/ai/config`、`/api/templates/reference-xlsx` 可匿名访问；`/api/projects`、`/api/report` 原本已校验）。
- **路径遍历加固**：静态文件改用 `path.resolve` + 大小写无关 + 分隔符感知前缀校验（URL 构造器本身已归一 `..`，编码变体不落地，此为纵深防御）。
- **Logo 上传内容校验**：仅允许 `data:image/(png|jpe?g|gif|webp)`，解码后校验 magic bytes（PNG/JPEG/GIF/WebP 文件头），限制 4MB，SVG 一律拒绝。
- **`esc()` 补单引号转义**（`'` → `&#39;`）。
- **登录/新建用户 placeholder 移除默认密码提示**（`index.html` 两处）。
- **fetch 15s 超时**：`api()` 内 `AbortController` 封装，超时抛「请求超时，请重试」；401 重试保持单次。
- **`uid()` 改 `crypto.randomUUID()`**：消除 6 位随机字符高并发碰撞风险。
- **`readBody` 非法 JSON 返回 400**：空 body 仍返回 `{}`（兼容）；新增全局 handler try/catch，异常统一走 400/413/500，不再裸抛崩溃进程。
- **AI 错误不泄细节**：AI 响应解析失败的原始内容只写服务端日志，客户端仅收到通用错误。
- **`tokens.user_id` 索引** + **`meta` 表迁移标记**：`migrateJson` 用显式标记防漏迁（用户已有项目时也记录"已迁移"）。
- **前端小项**：debounce 执行后清理 timer key；toast 加 `role="alert" aria-live="polite"`。
- **watchdog 错误边界**：周期回调 `Promise.allSettled` + try-catch，单次异常不再导致守护进程崩溃。
- **CORS**：应用为同源部署，不设跨域头即浏览器默认阻止跨域读取（安全默认），维持现状不放开。
- **暂缓项**：Token 改 HTTP-only cookie（需配套 CSRF 防护，改动大、个人部署收益有限，待评估）；报告按 assignee 聚合（schema 变更，需产品确认口径）；N+1/全量重建/事务封装/前端重构/公式拓扑排序等维持中期节奏。
- **验证**：临时实例实测——无 token GET templates→401、readonly→200、登录（旧哈希兼容）200、带 token 200、非法 JSON→400、路径遍历→404、假图片/SVG→400、合法 PNG→200。
