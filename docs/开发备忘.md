## 2. 启动与部署（双实例）

```bash
npm install
node server.js          # 正式版：端口 5181（PORT=5181，真实数据，写操作需令牌 data/auth.token）
node server.js --demo   # 演示版：端口 5180（脱敏数据 + 免令牌，公网隧道指向它）
node watchdog.js        # 守护双实例：5180 演示 + 5181 正式，崩溃各自自动拉起 + 维护 Cloudflare 隧道
```

- **端口约定（勿改）**：5180 = 演示版（公网评委用）；5181 = 正式版（本机日常用）。
- **公网网址（固定，不再变化）**：`https://kanban.forestkopa.top`（Cloudflare Named Tunnel `kanban-demo`，指向 5180 演示版，脱敏免令牌，评委用）。已固化进 `watchdog.js`，重启/崩溃自动恢复，域名永不变。
- 隧道机制：域名 `forestkopa.top` 的 NS 改到 Cloudflare（jack/joan.ns.cloudflare.com），Zero Trust → Networks → Tunnels → `kanban-demo` 挂 Public Hostname `kanban.forestkopa.top → http://localhost:5180`。本机 `cloudflared tunnel --config config.yml run` 持久化。
- 旧 `trycloudflare` 快速隧道已弃用（地址随机、不在 dashboard），`watchdog.js` 的 `ensureTunnel()` 改为只守护 Named Tunnel。
- 重启流程：`taskkill /IM node.exe /F`（连 cloudflared 一起杀也行）→ `node watchdog.js`（自动拉起双实例 + Named Tunnel）。
- 注意：`templates.json` 为两实例共享文件，demo 评委改模板会影响正式版模板。

### 2.1 demo / 正式版代码区分机制

同一份代码，靠 `DEMO_MODE` 开关分流（server.js L10 `process.argv.includes('--demo')`）：

| 位置 | 代码 | 作用 |
|---|---|---|
| L10 | `DEMO_MODE = process.argv.includes('--demo')` | 总开关：`--demo` 参数 |
| L15 | `PROJECTS_FILE = DEMO_MODE ? 'projects.demo.json' : 'projects.json'` | **数据文件隔离**（两版互不干扰的根本） |
| L38 | `if (!GIT_OK \|\| !file \|\| DEMO_MODE) return;` | demo 不自动 git 提交（评委乱改不污染版本库） |
| L417 | `if (DEMO_MODE) return;` | 空库播种示例项目仅正式版执行 |
| L489 | `authorized() { return DEMO_MODE \|\| 令牌匹配 }` | demo 免令牌；正式版校验 X-Auth-Token |
| L534 | `/api/readonly` 返回 `{ on, demo: DEMO_MODE }` | 前端据此显示「演示模式·免令牌」徽章、跳过令牌弹窗 |
| L917-918 | 启动日志带 `[演示模式]` / 打印令牌 | 运维区分实例 |

前端不自己判断：`loadAll()` 请求 `/api/readonly` 拿 `demo` 存 `state.demo`，`true` 时跳过令牌输入框。
watchdog 双实例：`SERVERS = [{port:5180, args:['--demo']}, {port:5181, args:[], env:{PORT:'5181'}}]`。

## 3. 业务规则（用户明确要求，勿改回）

### 3.1 看板列宽
- 列宽 = 6 列正好占满看板：`.col { flex: 0 0 calc((100% - 80px) / 6) }`（80 = 5×16 gap）。
- **少于 6 个阶段：不铺满，按 6 列尺寸排列、右侧留白**；恰好 6 个阶段一屏放满；超过 6 个阶段横向滚动（列宽保持）。
- 历史教训：固定 264px 在常见视口 6 列会溢出滚动（被否）；均分铺满 flex:1（被否，因为 <6 阶段也铺满了）。**当前 calc 方案是用户认可的**。

### 3.2 日报/周报/月报 + AI 总结 = 全局项目
- 四个视图（daily/weekly/monthly/panorama）**不依赖左侧选中项目**，`render()` 用 `globalViews` 分支，无选中项目也渲染。
- 项目集合 = `reportProjects(mode)`：全部进行中 + **归档项目仅在归档发生窗口内**（日报=当天、周报=当周、月报=当月，按 `completedAt`）。
- AI 总结按钮始终显示，`aiSummarize(mode)` 传全局项目；后端 `/api/ai/summarize` 支持 `{projects, mode}` 全局组合总结 + `{project}` 单项目兼容。

### 3.3 项目信息选项
- **工程师姓名 / 认证标签：纯手填**（无下拉/选项池——已按用户要求移除，勿加回）。
- 项目类型 / 产品类型 / 项目等级：**可配置**（`data/options.json`，gitignore 排除）——新增/编辑/删除，新增弹窗只留 **WPS 风格色板**（无自定义颜色行）；等级 S/A/B/C/D/E/F 默认色。
- 工程师**类型**（硬件/结构/项目/测试工程师）：可新增/删除（`options.engineerTypes`），姓名行=类型标签+手填输入框；保存为 `engineers: {类型名: 姓名}`，兼容旧 `hardware/structure/project` key。

### 3.7 深色主题
- `.btn.primary` 用独立变量 `--btn-primary-bg/--btn-primary-fg`（浅色=深底白字、深色=亮底深字），勿用 `var(--dark)` 做按钮背景（深色主题下 --dark 是浅色，会白底白字）。

## 4. 甘特公式级联引擎（关键机制）

- 导入解析只认「甘特方言」：有 `内容` 列、无 `阶段` 列、日期在 **D/E 列**、`天数`在 **F 列**、单元格带 `WORKDAY.INTL(...)` 公式 → 捕获 `startRule/dueRule` → 甘特级联。
- 参考模版列布局：`任务|内容|负责人|开始|截止|天数|状态|备注`；首任务开始 `=WORKDAY.INTL($B$1,0)`（B1=项目开始日期），后续 `=WORKDAY.INTL(E上一行,1)`，截止 `=WORKDAY.INTL(D本行,F本行-1)`。
- `evalRule` 的 `off` 类型：base 是数字（F 列天数）时做数值偏移，不是日期（曾因把 F4-1 当日期导致级联 NaN，已修）。
- 状态列默认留空（写"未完成"会被 `/完成/` 误判已完成）。

### 8.1 每次 push 同步 release（约定）
- 用户要求：每次 push 到 GitHub 必须同步更新 Release。已落地为**脚本方案**：用 `tools/sync-release.ps1` 代替裸 `git push`。
  - 用法（powershell）：`$env:GH_PAT="ghp_xxx"; .\tools\sync-release.ps1` → 自动 `git push origin main` + 移动 `latest` 标签到最新提交 + 调 GitHub API 更新 `latest` Release 元数据（指向 main 最新提交）。
  - Release 命名为 `Latest (main)`，标签 `latest` 始终滚动指向 main 最新提交；历史语义标签（如 `v1.0`）保留为里程碑。
- **为什么不用 GitHub Actions 工作流**：曾写 `.github/workflows/release.yml`（push main 自动更新 latest release），但推送被拒——当前 PAT 仅有 `contents` 权限、**缺 `workflow` 作用域**，无法推送 workflow 文件。若日后给 PAT 加 `workflow` 作用域，可改回 CI 自动同步（工作流内容已设计好，逻辑同脚本）。
- 首版 `latest` Release 已通过 API 创建并指向 `0560bbf`（README 更新提交），后续经脚本滚动同步。
