# 单实例与鉴权模型

一份代码、一个进程、一套真实数据。原先的 `--demo` 演示版分流机制已在 2026-09-11 彻底移除（过程见 [[19-演示版下线与单实例改造]]）。

## `--demo` 下线守卫（防呆）

```js
if (process.argv.includes('--demo')) {
  console.error('[启动失败] --demo 演示版已于 2026-09-11 下线，请直接运行 node server.js（端口 5181）。');
  process.exit(1);
}
```

**为什么必须退出而不是「静默忽略」**：忽略会让它带着 `PORT` 默认值在 **5180** 上再起一个实例，与 5181 双写同一份 `data/app.db` —— 两个进程同时写 SQLite，数据损坏风险极高。宁可启动失败，也不能悄悄跑起来。

## 鉴权：多用户 token

- 客户端带 `X-Auth-Token`（或 `Authorization`）。
- 服务端 `resolveUser(req)` 逐请求解析：拿 token 查 SQLite `tokens` 表 → 取用户；查不到返回 `null`。
- `authorized(req) => !!req.user`。旧的单 token 文件 `data/auth.token` 兼容逻辑**默认关闭**（明文即 admin 钥匙，不安全），需显式 `KB_LEGACY_TOKEN=1` 才启用。
- 免鉴权白名单：`GET /api/readonly`、`/api/version`、`/api/latest-release`、`/api/ai/ollama-models`，以及待办导出（纯前端数据 → 服务端排版，不读库不写库）。

## 四种角色与三个判定函数

| 角色 | 含义 |
|---|---|
| `admin` | 管理员，全量可见可写 |
| `manager` | 副管理员，全量可见可写 |
| `member` | 普通成员，仅自己的项目 |
| `viewer` | 游客，**只读**全量项目（无写权限） |

判定统一收敛在三个函数，避免散落数组字面量导致越权：

```js
const CAN_ALL     = ['admin', 'manager', 'viewer'];  // 可读全量项目/任务（含 viewer）
const FULL_REPORT = ['admin', 'manager'];            // 报告聚合全量（viewer 仅看自己，防数据越界）
const MANAGERS    = ['admin', 'manager'];
canAllRole(role) / isManagerRole(role) / fullReportRole(role)
```

> `viewer` 刻意**不在** `FULL_REPORT` 里：它能看到全部项目，但按人聚合报告只给自己——两者是不同维度的权限。

## 首登强制改密闸门

```js
if (req.method !== 'GET' && req.user && req.user.role !== 'viewer' && db.usesDefaultPassword(req.user.id)) {
  // 拦下写操作，要求先改密
}
```

- 只拦**写操作**；GET 放行。
- 排除 `viewer`：游客本就无写权限，不该被改密弹窗骚扰。
- 默认密码 `000000`（测试用）与首登 `mustChange` 标记由登录接口 `/api/login` 返回。

## `/api/readonly` 与实例标记

```js
GET /api/readonly → { on: <bool>, tag: <string> }
```

- `on`：全局只读开关（`data/readonly.flag`）。
- `tag`：**实例标记**，取自环境变量 `KB_INSTANCE_TAG`，原样回显。测试 harness 拉起隔离实例时注入随机串，轮询到这个串才算就绪——避免端口被别的进程占用时「连上就算通过」而测错实例。
- 前端不再据此判断"演示模式"（该机制已删），只用于就绪探测。

## 数据与模板路径

| 环境 | 数据库 | 模板文件 |
|---|---|---|
| 正式部署 | `data/app.db` | 项目根 `templates.json` |
| 隔离实例（`KB_DATA_DIR`） | `<临时目录>/app.db` | `<临时目录>/templates.json`（首次从项目根复制种子） |
