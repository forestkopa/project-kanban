# 一键升级异步化与进度条设计

## 背景与问题

v1.4.3 之前「一键升级」是**同步链路**：
- 前端 `await api('/admin/upgrade/confirm', { timeout: 300000 })` → 服务端 `await applyUpgrade()`（下载 40MB + robocopy 备份 + 解压 + Restart-Service，约 30-90s）才返回
- 公司宽带 + Cloudflare 隧道下经常 30-60s，触发前端 abort
- **结果**：服务端其实升级成功了（detached 进程跑完了下载/解压/重启），但前端 15s 超时报"请求超时，请重试" → 用户以为失败
- 黑屏等待 30-90s 无任何反馈，体验差

这是 v1.4.3 → v1.4.4 → v1.4.5 三次迭代的**核心矛盾**。单纯拉长前端超时（v1.4.4 的 `timeout: 300000`）治标不治本——总有个边界。

## 设计：服务端后台任务 + 前端轮询 + 进度条

v1.4.5 重构为**异步任务模型**，彻底解耦"立即响应"与"实际执行"。

### 1. 服务端 `lib/upgrade.js` — 任务状态机

```
任务生命周期: idle → download(0-70%) → backup(70-85%) → extract(85-98%) → restart(98-100%) → done
                                                       └→ error (任意阶段失败)
```

- 新增 `tasks` Map: `taskId → {phase, progress, message, error, finished, ...}`
- 新增 `startUpgrade(root, token)`: 验证 token → 生成 taskId → **立即返回** `{ taskId }`（<200ms）→ 后台 detached 任务跑全链路，每阶段调 `setTask(taskId, {phase, progress, message})` 更新状态
- 新增 `downloadFileWithProgress(url, dest, onProgress)`: **流式下载**（不再 `arrayBuffer()` 全读再写盘），边下边 `fs.createWriteStream().write()`，每 chunk 调 `onProgress(received, total)` 推送 percent
- 旧 `applyUpgrade` 保留作兼容（老代码/测试用）
- 任务完成后**保留 10 分钟**（TASK_TTL），让前端重连能拉到最终结果

### 2. 服务端 `server.js` — 三端点

- `POST /api/admin/upgrade/prepare` — 不变
- `POST /api/admin/upgrade/confirm` — 改调 `startUpgrade`（不再 `await applyUpgrade`）
- `GET /api/admin/upgrade/status?taskId=xxx` — **新增**，返当前任务快照

### 3. 前端 `app.js` `doUpgrade` — 轮询 + 进度条

```js
// confirm 阶段：<200ms 即返 taskId（不可能超时）
const r = await api('/admin/upgrade/confirm', { method: 'POST', body: ... });
const taskId = r.taskId;

// 启动 1s 轮询
pollTimer = setInterval(async () => {
  const st = await api('/admin/upgrade/status?taskId=' + taskId, { timeout: 10000 });
  // 更新进度条 + 阶段文字
  setBar(st.progress, st.message, color);
  if (st.finished) { stopPoll(); /* 终态展示 */ }
}, 1000);
```

### 4. 前端 HTML/CSS — 底部进度条

`#verBar` 浮在 footer 上方（`position:fixed; bottom:26px; backdrop-filter:blur(4px)`），含 8px 圆角进度条 + 阶段文字。升级中显示，结束隐藏。

## 为什么彻底解决"假失败"

**关键洞察**：v1.4.5 后端 `confirm` 端点 **<200ms 内返 taskId**。这意味着即便生产机仍是 v1.4.4 旧前端（`timeout: 300000` 但 5 分钟仍可能不够）：

- v1.4.4 旧前端 `await confirm` 立即成功（200ms 远小于 5min）
- 服务端后台跑完，30-90s 后浏览器硬刷新即见 v1.4.5
- **旧前端不会再"假失败"** —— 这是异步化的最大收益

## 任务状态保留 10 分钟的好处

- 升级途中浏览器关掉/卡掉 → 重开页面**只要 taskId 还在**就能拉到最终结果
- 升级途中网络断 → 轮询单次失败 `try/catch` 吞掉，下轮重试
- 避免"完成但不知道完成"的状态丢失

## 经验教训

- **同步长操作 = 隐形坑**：前端 `await` 同步等长任务，前端超时永远比真实耗时短。**任何 >10s 的服务端操作都应改异步**
- **进度条是 UX 必需品**：黑屏等待 30s+ 用户会以为卡死，分阶段 + 进度数字让用户放心
- **任务状态内存 Map 即可**：单实例个人项目，进程重启即丢任务状态（升级最后一步就是重启，OK）。分布式才需要持久化
- **流式下载 + 进度回调**优于 `arrayBuffer()`：内存友好、用户能看到实时进度、失败时能 abort

## v1.5.5 补课：异步任务 ≠ 服务不阻塞（2026-09-10 生产复现）

上面这套「后台任务 + 轮询 + 进度条」在 v1.4.5 上线后，生产上**依然表现成"升级卡死"**：
点一键升级 → 页脚卡在「服务重启中…（70s）请稍候」→ 公网 `kanban.forestkopa.top` 连续数分钟 502。
用户每次只能放弃、改为「停服务 → 手工覆盖 → 起服务」。**在线升级在服务器上从没成功过。**

### 根因（本机等价复现，硬证据）

线程模型搞错了：`startUpgrade` 虽然用 async 立即返回 taskId，但**任务体内部仍在用同步子进程**：

| 阶段 | 实现 | 代价 |
|---|---|---|
| 备份 | `cp.execSync('robocopy ...')` | 事件循环冻结数秒 |
| 解压 | `cp.spawnSync(tar.exe -xf ...)` | **事件循环冻结 97 秒** |

`spawnSync` 阻塞的是**整个 Node 事件循环**——HTTP 端口在内的一切都不再响应。
于是"后台任务"照样把服务冻死，前端轮询必然全部超时，只能一路显示「服务重启中…」。
更糟的是解压包里塞了 **1047 个 `node_modules` 文件**（1139 个文件里的 86%），把冻结时间从秒级拉到分钟级。

复现时间线（本机等价环境，含跑着的 watchdog）：

```
09:30:32 下载完成(22.5MB) → 09:30:36 备份完成 → 09:30:36 开始解压
09:30:36 ─────────────── 97s 端口 100% 无响应 ─────────────── 09:32:13 解压完成
期间 watchdog 记了 8 次「未响应 → 重新拉起 server.js」（全部撞 EADDRINUSE 空转）
```

升级最终其实成功了（版本号变了），但**用户视角就是"卡死了"**——这是最坏的一种 bug：功能对了、体验骗人。

### 修复（六项）

1. **`extractZip` / `backupDir` 改异步 `spawn`**：升级全程事件循环不再冻结，端口始终可响应。
2. **真实进度上报**：tar 带 `-v` 逐行计数 + 读 zip EOCD 拿条目总数 → 前端看到 88%→95% 在动。
3. **升级包不再携带 `node_modules`**（`build_update_zip.py` 默认排除，`--with-deps` 可退回）：
   1139 文件/22.5MB → 92 文件/2.8MB，解压 97s → 9s。附带收益：不再覆盖运行中的依赖目录
   （此前备份目录恰好排除 node_modules → 依赖被覆盖坏就回滚不回来）。
4. **依赖自检**（`missingDeps`）：不带依赖了，就必须在升级流程里查 `package.json.dependencies`
   是否已装，缺则**明确报错**（提示 `npm install --omit=dev`），绝不留给重启后 500。
5. **硬超时**：备份/解压各 5 分钟上限，卡死不再无限期占着升级锁。
6. **锁心跳 + 过期锁忽略**：锁文件内容 = 时间戳，升级全程 30s 刷新一次；
   进程若在升级中被杀，残留锁超过 3 分钟无人刷新即被判过期（此前残留锁 = 热重载与自愈永久失效）。
   另：解锁先写时间戳 `0`（= 过期标记）再尝试删除——Windows 上删除可能被杀软/权限/安全策略拦截，
   删不掉也不会让锁继续生效。

### 修后复验（同一套等价环境）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 解压耗时 | 97s | **9.1s** |
| 端口不可达时长 | 37s（且持续到 118s） | **1s**（重启瞬间） |
| 升级总耗时 | 118s | **24.3s** |
| watchdog 重复拉起 | **8 次** | **0 次** |
| 前端可见 | 只有「服务重启中…」 | 88%→94% 真实进度 |

### 一句话教训

**"改异步"要改到阻塞点上**：把 API 改成后台任务只解决了"前端等不等"，
真正的阻塞在 `spawnSync`/`execSync` 这种同步子进程调用上——它冻的是服务器自己。
判断标准很简单：**升级过程中，服务端口还能不能答话。**
