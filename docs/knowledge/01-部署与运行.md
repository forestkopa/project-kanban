# 部署与运行

多项目管理个人看板的本地运行与部署。**单实例架构**：只有一个正式版进程，真实数据、写操作需登录。

> 历史：2026-09-11 前为「双实例」——5180 演示版（`--demo` 脱敏数据 + 免登录）+ 5181 正式版并行。演示版已彻底下线，详见 [[19-演示版下线与单实例改造]]。

## 启动命令

```bash
npm install
node server.js          # 正式版：端口 5181（真实数据，写操作需登录）
node watchdog.js        # 推荐：崩溃自动拉起 + 维护 Cloudflare 隧道
```

`--demo` 参数已下线，带该参数启动会**直接退出并报错**（防呆，见 [[02-单实例与鉴权模型]]）。

## 端口约定（勿改）

| 端口 | 用途 | 数据 | 鉴权 |
|---|---|---|---|
| 5181 | 正式版，本机日常 + 公网 | 真实（`data/app.db`） | 需登录（`X-Auth-Token`） |
| 5180 | **已下线**（旧演示版） | — | — |

- 公网网址固定：`https://kanban.forestkopa.top`，读 `data/tunnel-url.txt` 核对。
- `config.yml` ingress 指向 `http://localhost:5181`（**指向正式版**，不是演示版）。
- 重启流程：`taskkill /IM node.exe /F` → `node watchdog.js`。

## 三层守护结构

```
kanban-watchdog（NSSM 服务，开机自启、Session 0）
  └─ watchdog.js（15 秒端口探活；按文件 mtime 自动 reload）
       ├─ server.js  → :5181
       └─ cloudflared → kanban.forestkopa.top
```

- **agent 侧杀不掉 / 重启不了** watchdog 服务：它在 Session 0、由 NSSM 托管。改 `server.js` 后 5181 行为不变 → 先怀疑服务没重载，须用户提权 `net stop|start kanban-watchdog`。
- 具体误判/重复拉起的坑见 [[18-守护进程误判与重复拉起]]。

## 隧道模式（2026-08-25 恢复本机模式）

- 曾计划隧道迁至 NAS（systemd cloudflared.service）；因 NAS 暂不支持 Ubuntu VM，**恢复本机跑隧道**（watchdog 守护）。
- watchdog 隧道守护 = **公网健康探测**（https.get kanban.forestkopa.top，6s 超时）+ 不可达时 taskkill 残留后重启 cloudflared（`tunnel --config config.yml run`）。
- 教训：**进程存在 ≠ 隧道健康**——曾残留僵死 cloudflared.exe 骗过"进程检测"导致公网 530；故改用公网探测。
- 开发机（DESKTOP-VOP181G）不跑 cloudflared，须 `KANBAN_NO_TUNNEL=1`；服务器（公司宽带 Win10）才跑隧道。
- cloudflared 位置：`C:/Users/Administrator/.cloudflared/cloudflared.exe`（v2026.8.2）；config.yml 在项目根。

## 开机自启：NSSM 服务方式（2026-08-25 定案）

- 服务名 `kanban-watchdog`（NSSM 包装 node watchdog.js，开机自启、无需登录、崩溃 5s 自动重启）。
- 安装：管理员运行 `install-watchdog-service.bat`（**CRLF+ASCII 编码**，绝对路径调用 nssm，开头 stop/remove 容错清理残留）。
- 教训：bat 必须 CRLF+ASCII（UTF-8 无 BOM 会被 cmd 当 GBK 解析导致全命令乱码）；不要用 set 变量+引号嵌套。
- 运维：`nssm status/start/stop/restart kanban-watchdog`；日志 `data/watchdog-service.log`（1MB 轮转）；卸载 `nssm remove kanban-watchdog confirm`（需管理员）。
- 曾试启动文件夹 vbs 自启——本机环境拦截间接启动进程，**弃用**（kanban-watchdog.vbs 已从启动文件夹移除）。

## 模板文件位置

- **正式部署**：项目根 `templates.json`（升级包会带上，便于随版本更新内置模板）。
- **隔离实例（测试）**：设了 `KB_DATA_DIR` 时，模板文件放进数据目录、首次从项目根复制一份作种子——既保证内置模板可用，又避免测试里的导入/改名写脏仓库文件。
