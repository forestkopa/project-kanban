# 守护进程的两类误判（源站 5xx / 端口无响应）

守护进程最大的破坏力不是"不干活"，而是**干错活**：一次误判会自己制造出一个比原故障更长的中断。
2026-09-10 排查生产「在线升级卡死 9 分钟」时，抓到 watchdog 的两个这类误判。

## 误判一：源站 502 被当成「隧道故障」

```js
// 原实现（有问题的判据）
const req = https.get(TUNNEL_URL, r => resolve(r.statusCode >= 200 && r.statusCode < 500));
```

这条判据的隐含假设是「只有 2xx/4xx 才算隧道通」——但**源站挂掉时，Cloudflare 返回的正是 502**。
于是升级期间源站短暂不响应 → 公网 502 → watchdog 判定「隧道挂了」→
`taskkill /F /IM cloudflared.exe` + 重拉 + **90 秒冷却**。

破坏链条：

```
源站短暂不可用（10-30s，正常重启窗口）
  → 公网 502
  → watchdog 以为隧道坏了，杀 cloudflared 并进入 90s 冷却
  → 公网持续不可达 90s+
  → 15s 后再判一次，可能又一轮
  → 用户看到的是「升级把服务搞挂了 9 分钟」
```

**正确判据：区分「谁的问题」**

| 现象 | 判断 | 动作 |
|---|---|---|
| 公网不通 + **本机源站正常** | 隧道/出网问题 | 重启 cloudflared |
| 公网不通 + **本机源站也不响应** | 源站问题（服务未起/正在重启/正在升级） | **什么都不做**，让源站守护去处理 |
| 公网不通 + 升级锁生效 | 升级窗口，属预期 | **什么都不做** |

闸门必须可自愈：源站恢复后，隧道守护要恢复正常重启能力（不能一次误判后永久屏蔽），
所以「源站不响应」时只是跳过本轮、不累计失败计数。

## 误判二：端口无响应 = 进程崩了

```js
if (await isUp(port)) { /* ... */ }
// 端口不响应 → 直接 spawn 一个新 server
spawn(NODE, [SERVER, ...]);
```

但「端口不响应」有两种截然不同的成因：

1. **进程真没了**（崩溃/被杀）→ 必须拉起
2. **进程还活着，只是事件循环被占住**（同步 IO / 启动中）→ 拉起毫无意义，只会撞 `EADDRINUSE`

第二个成因在真实升级里必然出现：`spawnSync` 解压把事件循环冻住 97 秒，
watchdog 每 15s 判定一次"挂了"，**连拉 8 个重复实例**（全部空转退出），日志被刷满。

**正确判据：看端口监听者还在不在**

```js
const listenPid = pidOfPort(port);   // netstat -ano 里找 LISTENING 的 PID
if (listenPid) {
  // 进程存活 → 忙碌，按宽限期跳过（锁生效时宽限期拉长）
  if (++busyTicks <= grace) continue;
  // 持续超过宽限期仍不响应 → 判定僵死，精确 kill 这个 PID 再拉起
}
// 无监听者 → 真崩了，直接拉起
```

宽限期给了"忙碌"足够的容错，同时保留「僵死兜底」：无锁 4 轮（≈60s）、
升级中 60 轮（≈15 分钟），超过就精确 `taskkill /F /PID <listenPid>` 再拉起——自愈能力没有丢。

## 通用法则

1. **健康检查要回答"是谁的问题"**，不能只回答"通不通"。凡是多跳链路（客户端 → CDN/隧道 → 源站），
   必须**分层探测**，否则上游永远替下游背锅。
2. **"重启"是最贵的动作**（带冷却、带中断），只在归因明确时才做；归因不明时宁可少做。
3. **端口无响应 ≠ 进程死亡**：先查监听者 PID，再决定要不要拉新的。
4. **误判的破坏力与被守护对象的恢复时间成正比**：源站 10 秒的问题，误判能造成 10 分钟。
